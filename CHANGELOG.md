# Changelog

All notable changes to Lynx are documented here, in reverse chronological order. Kept as short, scannable headlines - see the git history for full detail on any entry.

## 2026-08-25

**Fixed**
- The PipeWire tools package is `pipewire-bin`, not `pipewire-utils`. The wrong name had been in the overlay's own "is pipewire-utils installed?" error message for some time, and adding it to install.sh's package list on the strength of that aborted the whole install with "Unable to locate package" - taking everything after it, including the autostart repair below, with it. Corrected in install.sh and in both error messages, which were the very things anyone would have read while trying to work out what to install.
- The labwc autostart entry now invokes the start script through bash rather than running it directly, so a missing execute bit can no longer stop a receiver starting. The bit is not preserved by every route a file takes onto a Pi - SFTP drops it, and a file copied by hand rather than pulled arrives without it - and when that happened the autostart failed SILENTLY: no picture, no overlay, nothing in any log, just the bare desktop with no indication why. install.sh also repairs an autostart written the old way, on every run including Update Now, so existing receivers are fixed without anyone needing to know this was ever a problem. The explicit chmod remains, since someone typing ./lynx_start.sh by hand still needs it, and now covers install.sh as well.


**Fixed**
- The display is capped at 1080 lines, switching a 4K output to 1920x1080 at startup. A 4K framebuffer is more than this hardware can sustain alongside decoding a live DATV stream: confirmed on a Pi 5 with 16 GB free and 88% idle CPU - so neither memory nor compute - where 3840x2160 gave picture glitches and audio dropouts, both markedly worse on fast-moving pictures, and stopped the OSD overlay appearing at all. The same receiver on the same transmission is clean at 1080. Nothing is lost, because DATV video is far below 1080 anyway (1024x576 is typical), so a 4K framebuffer only asks the display pipeline to composite four times the pixels for an identical picture - the monitor scales to its own panel regardless. An ultrawide at 2560x1080 is left alone, its height already being within the cap.
- Set from a new Screen card on the Config page, or `display.refresh_hz` (50 or 60, default 50) and `display.max_height` in the config file directly; `LYNX_REFRESH_HZ` and `LYNX_MAX_HEIGHT` override both for testing. Note that every save function touching the display section must send ALL of its fields: the API merges with `update(model_dump())`, and model_dump fills anything unsent with the model's default, so omitting a field silently resets it on disk. savePpmStyle() already carried audio_device for this reason; it and the new card now carry refresh_hz and max_height too. 50 Hz is preferred because a 25 fps source needs 3:2 pulldown at 60 Hz - frames held alternately for two refreshes and three - which shows as judder on any pan. A display offering no mode at the wanted rate falls back to the highest it does offer, since being left at 4K is the fault being fixed. Read with python3 rather than by grepping the YAML, so a reordered or commented line cannot quietly give the wrong value; a missing, malformed or nonsensical config falls back to the defaults rather than failing to start.
- Applied at runtime with wlr-randr, never in config.txt - the same reasoning as leaving UART settings to raspi-config. A wrong value in boot configuration needs a card reader to recover; this is undone by a reboot. `wlr-randr` and `pipewire-bin` added to install.sh, both having been assumed present rather than required.


**Changed**
- The scheduled reboot is now ENABLED by default and runs once a night at 03:00, rather than being installed-but-dormant and running twice daily at 04:00 and 16:00. A receiver is an appliance expected to run unattended for months, so a restart at a genuinely quiet hour costs nothing and clears anything that has slowly crept up which nobody has thought to look for. The afternoon slot was dropped because it fell in the middle of the day for anyone actually using the repeater, and nothing needs clearing that often. Still carries up to 5 minutes of jitter so several receivers on one site never drop together. Turn it off with `sudo systemctl disable --now lynx-scheduled-reboot.timer`.

**Fixed**
- The stack-trace logs now rotate at 2 MB. `/var/log/lynx/stacktrace.log` and `stacktrace_overlay.log` are opened for append by faulthandler and written to again by the watchdog, and unlike everything else in that directory they had no cap at all - so they grew across reboots indefinitely. About a kilobyte per incident, which is why it went unnoticed, but a fault recurring on an unattended site writes one every time: the HDMI hotplug case alone produced three inside a quarter of an hour.


**Fixed**
- Auto-Squeak now captures with `pw-cat`, exactly as the PPM meter has read the same monitor all along - same program, same flags, no extra environment. Asking ffmpeg's `-f pulse` input for large fragments, and setting PIPEWIRE_LATENCY alongside it, was the obvious fix and did not work: `-f pulse` is not a PipeWire client at all, it connects through the PulseAudio compatibility layer, and the negotiation that sets the graph quantum happens there regardless of what is requested further up. Confirmed in the field on a Pi 5 sitting 86% idle - stuttering on every codec with Auto-Squeak on, perfect with it off, so nothing to do with decoding. Deliberately no PIPEWIRE_LATENCY on the pw-cat path either: a large-quantum request is plausible but is reasoning rather than evidence, and it would make this tap subtly different from the one already proven.
- `pipewire-utils` added to install.sh. `pw-cat` was already required by the PPM meter - the overlay's own error message asks whether the package is installed - but it was never a stated dependency and worked only because Raspberry Pi OS happens to ship it. Two features now rely on it.
- Auto-Squeak settings documented in lynx_config.example.yaml, which had no `squeak:` section at all.


**Action required after updating**
- **Reboot the Pi by hand once.** "Update Now" runs whatever is already loaded in memory, so the update that delivers these fixes is still carried out by the code they replace. Every update after this one restarts on its own.
- **If Reboot, Shutdown or Kill WiFi still do nothing, run the installer once:** `cd ~/lynx && ./install.sh`. Those buttons need passwordless sudo. Raspberry Pi OS normally grants it to the first user, but not always - a user added later, or some headless setups, may not have it, and both receivers examined while fixing this turned out to lack it. `install.sh` configures it properly, but it needs sudo to do so, so it has to be run from a terminal where you can type your password once. It cannot be done from the Web UI, and no amount of updating will fix it on its own. After this release those buttons say so in the log rather than silently doing nothing, so you will know which situation you are in.

**Fixed**
- The Picotuner tuning watchdog could take the tune lock away from a tune already in progress. Its restore path called `_tune_impl()` directly rather than going through `tune()`, which is what acquires the lock - but `_tune_impl()` is written assuming the caller already holds it, and hands it to its own mpv thread to release in a `finally`. So the watchdog had a thread releasing a lock nobody had taken: `RuntimeError: release unlocked lock` in the log, and, far worse, the lock freed regardless of who was holding it. An operator tune underway at that moment lost the lock mid-sequence and two tune sequences then ran against the Picotuner at once, interleaving their commands. Reported as a receiver that was reachable, responsive and visibly healthy, but whose frequency simply would not change - and self-sustaining, because a restore that never completed left the mismatch in place, so the watchdog fired again on the next cooldown and kept doing so. The restore now takes the lock exactly as `tune()` does, and backs off if a tune is already running; nothing is lost when it does, since the watchdog still sees the mismatch and retries. Present on both channels.
- Auto-Squeak could put up a results card reading PASS with nothing measured on it. Two faults compounded: the trailing audio after the final segment header ran to the end of the capture buffer, and since capture deliberately continues for twelve seconds past the last header, that tail was measured as though it were a segment - classified as noise, and quiet enough to win the `min()` in the noise calculation. Meanwhile `_failures()` tested each measurement only if present, so a result carrying none at all fell through every test and rendered as a confident PASS. The last segment is now bounded by how long the other segments actually ran and dropped when there is nothing to infer that from, results with no segments are never published, and an absence of measurements reports itself rather than passing by default. Programme audio that trips the opening detector now produces no card instead of a clean bill of health.
- Passwordless sudo is configured by the installer rather than left to the operator. Reboot, Shutdown, Update and Kill WiFi all shell out to sudo, and stock Raspberry Pi OS usually grants it - but not always, depending on how the user was created, and when it is missing the buttons fail in a way that reads like a broken install. The rule is validated with `visudo -c` before being installed, so a malformed entry can never lock anyone out of sudo, and superseded `lynx-reboot`/`lynx-shutdown` drop-ins from the older manual instructions are removed. Uses `id -un` rather than `$USER`, which is not guaranteed to be set when the script runs from inside the Lynx process.
- Placed above the `--deps-only` exit, so it reaches receivers being updated and not only fresh installs - the same mistake, and the same fix, as the chrony setup on 2026-08-21.
- "Update Now" could sit for twenty minutes doing nothing visible and then not reboot. The dependency step runs `install.sh`, which needs sudo throughout - for apt, for writing to `/etc` - and on a receiver without passwordless sudo it stopped at a password prompt with no terminal to answer on, waiting out the full timeout in silence. It is now guarded by a blanket sudo check, run with stdin closed so any prompt fails immediately rather than blocking, and skipped with an explanation rather than attempted and hung. The reboot is judged separately and always attempted, so a receiver that cannot refresh its dependencies still restarts and still runs the new code.
- Every power action goes through one place, passes `-i`, and reports its own failures. Reboot, Shutdown, the post-update reboot and the channel-switch reboot were four separate call sites, three of them firing into a bare `Popen` with the result discarded - so a refusal left the button looking like it had worked, which is what turned a one-line error into a two-day hunt. `-i` is there because these go through logind, which can refuse while a user is logged in on seat0 - permanently true on a receiver, where the desktop user is auto-logged-in, and not something root overrides. Observed once refusing with exactly that message; not reproducible on demand afterwards, so `-i` is insurance rather than a proven cure, and the captured error is the part that actually matters. Shutdown now uses `poweroff -i` rather than `shutdown -h now`, which is the same systemd action but has no `-i`.
- The sudo instructions in those error messages could not be run as printed. Three commands separated by newlines inside a JSON error detail collapse to one line in a browser; pasted as a single line, `tee` swallowed the rest as filenames and reported `-c invalid argument`. Confirmed in the field. Replaced with one `&&`-chained command that survives being collapsed and validates the rule before installing it.
- The app log survives a reboot. It was written only to `/tmp`, which is cleared on restart - so the one event most worth having a log of was also the one guaranteed to destroy it, and a refusing Reboot button had to be diagnosed from a dropped SSH session two days later. Now written to `/var/log/lynx` as well when that is available, appended across boots with a dated start marker, rotated at 20 MB with one generation kept, and degrading quietly to `/tmp` alone if the directory is missing.
- `/var/log/lynx` is created above the `--deps-only` exit too, so it exists on receivers that have only ever been updated rather than only on fresh installs. Its absence was silent by design - both the app and the startup script fall back to `/tmp` - so it would have presented as "the persistent log doesn't work" rather than as a missing directory.

## 2026-08-24

**Added**
- Auto-Squeak: measures the receiver's audio chain from a Lindos test sequence and puts the results on screen - level against alignment in PPM, level error, channel balance, frequency response plotted 20 Hz to 20 kHz for both channels, noise, stereo separation and distortion. Runs in the background and is triggered by the frequency-shift keying that precedes each Lindos segment rather than by a level threshold, so programme audio cannot start it by accident. On by default; idle until a sequence arrives. Where a repeater runs Lynx this means any user can measure the transmission chain from their own shack simply by sending the sequence, with no test equipment at either end.
- Auto-Squeak follows whichever audio output is selected, using the same resolution the PPM meter uses rather than the system default sink - the meter originally watched the default, and with mpv sent to HDMI while a USB dongle was the default it sat reading silence with no indication why. The measurement would have failed the same way and looked like a broken detector rather than a misdirected one.
- Auto-Squeak and Pathfinder are queued rather than competing. At the end of a test transmission both fall due, since the station sending the sequence has transmitted like any other - so this is the normal case, not a rare clash. Auto-Squeak shows first and Pathfinder waits, keeping its full display window. Ordering matters because the measurement completes about twelve seconds after the last segment while Pathfinder arms within a few seconds of the drop, so without the queue the map would appear first and be pushed aside exactly as the figures arrived. Auto-Squeak also draws over live video, where Pathfinder deliberately never does: its results are wanted during the transmission, and what it covers is a test card.
- numpy added to install.sh, and `import lynx_squeak` in lynx_app.py made non-fatal. Auto-Squeak needs numpy, which was not previously a dependency, and anyone updating by copying files rather than running the installer would not pick it up - a missing optional feature must never stop the receiver starting, so it degrades to "Auto-Squeak unavailable" with a note in the log.
- Web UI manual: new section 3.12 covering Auto-Squeak, what each reading means, the settings, and how it interacts with Pathfinder.

## 2026-08-23

**Added**
- Pathfinder now draws a globe rather than a terrestrial map when the contact came via QO-100. A great-circle line between the two stations is actively misleading for a satellite contact - the signal went up 36,000 km and back down, not across the ground - so the card shows an orthographic globe with both ends marked and the satellite drawn where it really is. The view is tilted 12 degrees, which is what lets the bird sit at its true geostationary distance of 6.6 Earth radii and still land just clear of the limb, to scale, with no compression. Centred on the sub-satellite longitude, so the visible disc is very nearly the satellite's own footprint. Both ends are labelled by country, since the bundled town data is clipped to the UK and a country is the honest granularity at globe scale anyway.
- The BEARING column becomes DELAY on a QO-100 card. A bearing is meaningless when both stations point at the same satellite, whereas the propagation delay - around 253 ms for a European contact, computed per contact from the two slant ranges rather than quoted as a constant - is the thing everyone remarks on.
- Natural Earth 110m world land and country outlines added to `geo/` (about 800 KB). The existing 10m set is deliberately clipped to 1200 km around the UK, so it contains no Africa or Middle East to draw; 110m is also the correct resolution at globe scale, where 10m would be invisible detail that merely costs time.
- `pathfinder.qo100_test` in the config file forces the globe view on for any contact, so the card can be developed and demonstrated at a site with no 3cm satellite installation. Honoured by `/api/pathfinder/test` as well as real contacts. Deliberately not on the Config page: it makes every card wrong and is only ever wanted by someone editing the file by hand.

**Fixed**
- QO-100 detection tests the DOWNLINK, not the LNB local oscillator, so a 9750 Universal LNB, a 9000 QO-100 PLL LNB or anything else all give the same answer with no list of LOs to maintain. The Picotuner reports the IF and has no idea an LNB sits in front of it, so the LO is added back first - which is also why the decision is made in `lynx_app.py` and passed through rather than worked out in `lynx_map.py`, which never sees the LO. The test itself uses the IARU Region 1 / RSGB bandplan boundary (10475-10500 MHz, Amateur Satellite Service only) rather than the transponder edges: terrestrial 10 GHz ATV repeaters sit far below at 10065, 10240 and 10425 MHz, so nothing terrestrial can legitimately appear in that window and a frequency test is sufficient on its own rather than a heuristic.
- `max_distance_km` no longer rejects QO-100 contacts. That limit exists to catch a stale or default QRZ locator on a terrestrial contact, where several thousand km means bad data rather than an extraordinary contact - but via the satellite the reasoning inverts, since the footprint is most of a hemisphere and a South African or Brazilian station is entirely ordinary. Found in testing: ZR6TG at 9,000 km drew no card at all while nearer European stations worked.
- Missing globe map data now says so in the log instead of failing silently. A shapefile is three files (.shp, .shx and .dbf) and pyshp needs all of them; copying only the .shp left `_read_shp` catching the error and returning nothing, which drew a bare disc with two correct markers on it and read as a rendering bug rather than a missing file.

## 2026-08-21

**Added**
- Portable locator can now be set automatically from a GNSS receiver - a Waveshare L76K HAT on the Pi 500+'s GPIO header UART (`/dev/ttyAMA0`). A new "GNSS Portable Locator" card on the Config page offers three modes: Off (unchanged behaviour - the receiver isn't read at all), Automatic (the default - GPS overwrites the existing QRZ "Portable locator" field once a fix has held the same 6-character Maidenhead square for a full 30 seconds, so a moment's wander at a boundary can't flip the logged square), and Manual (GPS is shown for information only; the operator's typed value stays authoritative even with a HAT fitted and locked). This is not a new field - it drives the same `notifications.qrz.portable_locator` an operator already had to type by hand for QRZ's own distance/bearing calculation, exactly as anticipated when that field was first added. A fixed repeater site is entirely unaffected: no HAT means the reader fails quietly and portable_locator stays exactly as configured, forever, with no restart needed if a HAT is fitted later. Configures the L76K for GPS + BeiDou + GLONASS (mode 7, plus QZSS which is always on) on every connect, rather than the board's factory-default GPS + GLONASS only - the widest satellite visibility the module can actually be told to use.
- Top-row indicator (📍) shows the portable locator's value AND where it came from - live GPS or the configured value - so it's never ambiguous which one QRZ logging will actually use. Shows the extended 8-character locator when GPS-derived, for the finer indication; the 6-character value logged to QRZ is unaffected. Reads "No GNSS Module" outright, rather than folding it into the generic no-fix state, when the reader is enabled but nothing on the serial port is answering.
- No GNSS module detected: Automatic and Manual are greyed out on the Config page - disabled, dimmed, `cursor: not-allowed`, with the reason on a hover tooltip - the same treatment already proven for the PicoTuner's own absent LNB-plug-B buttons. Off always stays selectable as the escape hatch. Un-greys live, no reload, the moment a fitted HAT starts answering.
- GPS time sync via chrony's SOCK refclock driver, for portable operation with no internet and no RTC backup - previously such a receiver had no reliable clock at all beyond whatever it happened to boot with. Talks to chrony directly over its documented SOCK protocol rather than via gpsd, since gpsd would need exclusive ownership of the same serial port GnssReader already owns - no second process, no port-sharing conflict. With NTP servers also configured as normal, chrony's own mature source-selection algorithm picks whichever is actually reachable, with no custom preference logic needed on Lynx's side: NTP at home, GPS automatically at a remote site with no internet. Time is trusted as soon as a fix meets the same satellite-count/HDOP quality bar the locator itself uses - deliberately NOT also gated on the locator's own 30-second stability window, since GPS time doesn't need position to have settled into one square first the way the locator does; this matters most exactly when signal is marginal (indoors, under a heavy canopy), where waiting the full 30s would delay a perfectly trustworthy clock correction for no reason. Independent of the locator's own Off/Automatic/Manual mode - a separate toggle on the same Config card, since useful time sync and how the portable locator itself should behave are genuinely different questions. Requires a one-time addition to chrony.conf, shown directly on the Config card.
- LNB LO dropdown gained a 9000 MHz (9 GHz) option for QO-100, alongside the 9750 MHz standard, for the newer 9-10 GHz-range LNBs now available.

**Fixed**
- The "Video Switching (Bitfocus Companion / GPIO)" card relabel (see 2026-08-18 below) had silently reverted back to plain "Bitfocus Companion", along with its GPIO Tx cross-reference text - not a new regression, but a genuine casualty of the QuickLynx loadPresets revert on 2026-08-18: that fix rolled back the whole file to a commit before the relabel had ever been added, and nobody had reason to reapply it once QuickLynx was redone from that clean base. Restored, along with an audit of every other dated entry in this file against the actual running code, which turned up nothing else missing.
- A config-write race between GNSS's own automatic saves and a manual Config page save - both wrote to the same on-disk file via the same temporary filename with no lock between them, a latent gap that predates GNSS entirely (the update-channel switcher had the same exposure) but was made far more likely to actually bite by GNSS's high-frequency automatic writes landing at the same moment as a browser tab's save. Confirmed as the cause of a real, reported failure: QRZ logging stopped working entirely after this exact overlap during testing. One shared lock now serializes every writer of `lynx_config.yaml`.
- The portable locator was being submitted as ADIF's `GRIDSQUARE` field - the worked/contacted station's own grid, which QRZ already derives correctly from that station's own profile - instead of `MY_GRIDSQUARE`, the logging station's own field. Every contact logged with a portable locator set was carrying Lynx's own GNSS position attributed to whichever callsign happened to be logged, rather than correcting Lynx's own location as "operating portable" always meant. Fixed in `lynx_notifications.py`; every place describing the old (backwards) behaviour - the QRZ card's help text, the GNSS card's text, and the log line printed on each override - updated to match.
- GNSS mode Off didn't reliably stop a previously GPS-confirmed locator from still being submitted - the reader correctly stopped writing *new* values, but the last one already written wasn't cleared, so a contact logged at a fixed site with GNSS switched off could still carry a stale portable position from an earlier portable session. Off is now a hard guarantee at the point of submission, not dependent on the stored value happening to already be empty.
- GNSS's Off mode is removed entirely, replaced with a simpler Automatic/Manual choice - Off stopped the whole GNSS reader, GPS time sync included, which meant wanting GPS out of the locator cost you clock correction too, for no benefit: Manual already gives GPS-never-touches-the-locator with none of that downside. The receiver now always reads /dev/ttyAMA0 once running (a site with no HAT costs nothing either way - the reader fails quietly and keeps retrying forever); only whether a confirmed fix is trusted to drive the locator is configurable. Manual is now the always-selectable option regardless of hardware state, since unlike Automatic its behaviour doesn't depend on a HAT actually responding. The QRZ card's own portable-locator field also now live-updates from GPS while Automatic is selected, rather than showing a stale snapshot from whenever the page happened to load.
- GPS time sync's chrony setup in `install.sh` was placed after the point "Update Now" actually stops (`--deps-only`), meaning it only ever applied on a from-scratch install, never on an existing receiver being updated - exactly the situation most people adding this feature to an already-running Lynx would be in. Moved earlier; safe to run on every update since every step is already idempotent (checks before acting), unlike the config/autostart steps deliberately left below the `--deps-only` exit, which genuinely must not be redone on an already-configured system.

**Changed**
- install.sh cloned the repository's default branch (main) regardless of which branch the script itself was fetched from. The quick-install one-liner in the guide points at `.../beta/install.sh`, so running it produced a beta installer driving a main checkout. The failure was silent at the point it happened and only surfaced much later as `cp: cannot stat '/home/pi/lynx/lynx-scheduled-reboot.service'`, because the systemd units exist only on beta - an error that points at the symptom rather than the cause. Now clones an explicit branch (`beta` by default, overridable with `--branch main`), and warns if an existing `~/lynx` is on a different branch from the one being installed rather than silently proceeding against unexpected code.
- The scheduled-reboot unit copy was an unguarded `cp` under `set -e`, so a missing file aborted the whole install partway through and left a half-configured system. Now skipped with an explanatory message if the units aren't present: a scheduled reboot is an optional extra and isn't worth losing an otherwise complete install over.
- install.sh now sets up the GNSS socket permissions GPS time sync actually needs, which was the second of two reasons it had never worked on a real receiver. chrony creates its SOCK refclock owned by root:root and writable only by root, but Lynx runs as the desktop user and has to write samples into it - so even with chrony correctly installed and configured, Lynx connected and immediately failed with `[Errno 13] Permission denied`. Handled with a `gpsshare` group plus a systemd drop-in rather than a one-off chmod, because chrony recreates the socket on every start and a manual chmod is undone by the next restart. The drop-in uses a `+` prefix on ExecStartPost so it runs as root despite the unit's own `User=_chrony` - without that the chgrp fails AND takes the chrony service down with it, which is worse than having no GPS time sync at all; a trailing `exit 0` is the same insurance. Placed before the `--deps-only` exit like the rest of the GPS time-sync setup, so "Update Now" applies it to existing installs, and the closing summary notes that group membership only takes effect after a reboot or re-login.
- GNSS card's time-sync section cut back from about fifteen lines of chrony setup mechanics - including a raw `refclock` config line to paste and claims about what install.sh does - to a single sentence describing what the toggle actually achieves for the operator. The old text was also inaccurate: it promised setup was fully automatic when a normal install doesn't complete it (chrony's install step sat after the `--deps-only` exit, and socket permissions were never handled at all), so it was misleading as well as overlong. Status strings changed for the same reason - "Not reaching chrony - check chrony.conf" told operators to go and edit a system config file, which is exactly the support call the card should prevent; now reads Off / Active / Unavailable on this receiver / Waiting for a fix. The mechanism stays documented in code comments for whoever maintains it.
- Audio Output device dropdown was missing the dark-theme classes every other dropdown on the Config page has, rendering with a stray white background. Now consistent with the rest of the page.
- QuickLynx Spectrum Tuner card moved to the bottom of column 3; Slack card moved to the bottom of column 1.
- "Save GNSS mode" only ever saved gnss.mode/time_sync, not the QRZ card's portable_locator field sitting right above it - switching to Manual and clearing the locator field looked saved (the field visibly went blank) but wasn't, since only "Save QRZ settings" actually persisted that field. Confirmed as the cause of a real, reported bug: GPS's last-written locator from an earlier Automatic session kept appearing in the logbook after switching to Manual, since the backend never learned the field was now meant to be empty. "Save GNSS mode" now submits the QRZ card's current values too, so one save covers both.
- Config page's dark theme was missing three things it had always been missing, only now visible on newly-added elements: `.form-select` (a genuinely different Bootstrap 5 class from `.form-control`, used for `<select>`) was never styled at all, so the audio device dropdown - the one select using it instead of the form-control-on-a-select convention every other dropdown on this page already uses - fell through to Bootstrap's own light default; a `bg-dark` fix attempted earlier made it worse (near-black, fighting the theme with `!important`) rather than fixing the actual gap, now removed in favour of a proper `.form-select` rule matching `.form-control`. Disabled inputs (the QRZ card's portable-locator field while GNSS Automatic drives it) had no `:disabled` override, falling back to a stark, out-of-theme light box - now stays dark with dimmed text. Native `<input type="time">` chrome (GPIO Tx's schedule fields) doesn't respond to plain `background`/`color` CSS on the outer input at all - needs `color-scheme: dark`, which every date/time input on the page now has.
- Top-row status controls (Picotuner LED, LNB A/B buttons, mode/locator/version badges, update controls) had no `flex-wrap`, meaning a narrow browser window could silently overflow content off-screen rather than wrapping it to a second line - a latent risk that got more likely to actually bite once the locator badge added yet more content to an already-crowded row. Now wraps gracefully instead.

**Added**
- QRZ submissions now log the exact outgoing ADIF payload (API key redacted) and QRZ's own raw response to stdout, unconditionally, for every logged contact - added specifically to settle whether an unexpected logged locator is something Lynx sent wrong or something QRZ's own handling did with a correctly-sent value, rather than guessing from either end.

**Fixed**
- The first contact logged right after a restart could carry the literal text "None" for MER and a blank modcod, rather than real values. Traced to a genuine startup race: the lock/callsign broadcast (port 9997) and the quality broadcast carrying MER/modcod (port 9901, read by a completely separate background thread, `picotuner_quality_monitor()`) don't start in lockstep, so QRZ's settle timer could fire in the gap before quality data had arrived at all - `to_float("")` on the not-yet-populated default correctly returns `None`, which then string-interpolates as the literal word "None" in the logged comment. Now deferred a few seconds (bounded to 3 retries) rather than logged incomplete, re-reading live Picotuner state fresh on each retry so it picks up MER/modcod the moment they genuinely arrive; still logs anyway after the retry budget rather than silently dropping a contact if quality data never turns up. Scoped to normal/diversity operation only - tri_watch's own per-receiver source data is a separate, already-independent tracking path this doesn't touch.
- The above fix checked MER alone as a stand-in for "quality data has arrived", which turned out to be an incomplete proxy: entries kept appearing with a real MER but still missing the "QPSK 8/9" modcod suffix. Traced to a genuinely separate source - MER (and margin) can also arrive via `picotuner_table_monitor_b()`, a THIRD background thread that explicitly only ever backfills tuner A's MER/margin, never modcod, which comes solely from `picotuner_quality_monitor()`'s own parsing. The retry now checks both independently.
- Pathfinder's end-of-contact card could show blank MER/modcod for the same underlying reason as the QRZ fix above, but via a different mechanism: the telemetry snapshot was read synchronously, before the QRZ name/locator lookup thread even started - meaning it was frozen well before that lookup's own network round-trip completed, throwing away however many seconds `picotuner_quality_monitor()` might have used to actually deliver fresh data in the meantime. Most visible on short contacts made soon after a restart. Telemetry is now read after the lookup completes, immediately before the card is actually armed, giving it the most possible time to be genuinely current.
- The fix above traded one bug for a worse one: reading telemetry after the QRZ lookup completes meant a genuinely different, later transmission starting during that lookup's several-second delay could silently overwrite `picotuner_state` before it was read - the card would show a second station's still-settling MER, misattributed to the first. Confirmed as a real, reported case on a close-range test link doing rapid back-to-back transmissions (24.3dB logged vs 10.0dB shown on the card for the same contact). `picotuner_state` has no concept of which QSO it belongs to, so the only correct fix is capturing the snapshot the moment the unlock event actually fires, before anything else can touch it - moved back to that, with the original "quality data not arrived yet" case now handled by its own short (up to ~2s), bounded wait, kept deliberately separate from and much shorter than the QRZ lookup's own unrelated, unpredictable duration.
- That ~2s bounded wait was a guess, not a measurement, and live testing disproved it immediately: a card from the exact restart scenario it exists for still came back with no MER or modcod at all. Re-anchored to ~8s instead, based on the QRZ side's own retry budget (3 retries x 3s, proven working via a confirmed complete log entry) rather than guessing again - still meaningfully shorter than the QRZ lookup's own up-to-10s timeout, so the original point of capturing the snapshot before that lookup starts (bounding how long a later signal could overwrite state) still holds.
- Root cause finally found, and it was neither of the two things the previous entries assumed. Pathfinder's card was missing MER and MODCOD because `picotuner_quality_monitor()` rebuilds those fields from every Picotuner broadcast using `fields.get('$12', '')` / `fields.get('$18', '')` - so the instant a signal drops and the tuner stops sending them, both are overwritten with empty strings, typically within ~500ms and always before the end-of-contact handler runs. Reading them at unlock was an unwinnable race, which is why the original code, and both attempted fixes, all failed the same way. Confirmed live by diagnostic logging: a print inside `_pathfinder_arm()` read `mer='10.8'`, `modcod='QPSK 8/9'`, and the snapshot taken on the very next line captured `''` for both. The clue that separated this from a rendering fault was that `symbol_rate` and `frequency` always survived - they aren't blanked on that transition. Telemetry is now cached continuously by `pathfinder_watcher()` while the signal is still live and passed into `_pathfinder_arm()`, which no longer touches `picotuner_state` at all. The bounded waits added by the two previous attempts are removed: the data was never late, it was being destroyed, so waiting made things strictly worse.
- The actual, underlying cause of the missing Pathfinder MER/MODCOD - and of MER and Margin showing blank on the Tuner Rx 1 status card generally - turned out to be shared ownership of `picotuner_state`. Two background threads write tuner A's `mer` and `margin`: `picotuner_quality_monitor()` reads explicitly TAGGED fields from port 9901 (`$12` = MER, `$30` = margin), while `picotuner_table_monitor_b()` reads fixed whitespace COLUMN POSITIONS from the table broadcast on 9904. Those column positions aren't stable across firmware revisions, so on `ptwh0v3k-w5100s` the second thread overwrote correct values with non-numeric junk roughly twice a second. Proven with tcpdump: the packets carried `$12,25.0`, `$18,8PSK 8/9`, `$30,14.3`, `$31,H265` correctly while the Web UI showed MER and Margin blank. The giveaway was that MER and Margin - exactly and only the two fields the table monitor writes - were the ones lost, while `$9` (symbol rate) survived because nothing else touches it. The positional writes are now guarded to apply only when those columns genuinely hold numbers, so tagged data always wins. A full audit of every field in `picotuner_state` and `picotuner_state_b` confirms these were the only two fields anywhere with more than one writing function; the hazard is now documented in the function's own docstring so it isn't rediscovered the hard way.
- Follow-up on the above, prompted by a report that this symptom had appeared and cleared *randomly* over a long period rather than being permanently stuck: a numeric-only guard on the positional writes wasn't sufficient. This table's rows are variable-width - already documented for Rx2, where the existing code searches for values rather than trusting positions, and the same acquisition-stage variation applies to the Rx1 row. So a shifted layout can place a genuine but WRONG number at the column positions being read, which passes a numeric check and silently corrupts a good reading instead of blanking it - values that look plausible, are wrong, and come and go depending on what the tuner happened to include in that row. The Rx1 supplement is now restricted to the single case it was actually added for: when the tagged 9901 source has no value yet (unlocked/searching). Once tagged data is flowing it is authoritative and is never overwritten from column positions. Confirmed safe because the tagged source resets `mer` to empty whenever `$12` is absent, so the supplement still engages whenever it is genuinely needed.
- Pathfinder's card reported an MER far below what the contact actually achieved (25.0 dB live on the tuner, 3.7 dB on the card, worse again on a repeat transmission). The telemetry cache added above overwrote its stored MER on every poll, so the value that survived was whatever the final poll caught - which is the signal already collapsing as the operator unkeys, not the quality of the contact. Now keeps the BEST MER seen during the contact, with margin captured from that same poll so the two stay consistent with each other. Also verified during this investigation, and worth recording since an earlier changelog entry above assumed otherwise: the table monitor's column indices (`parts[3]` = MER, `parts[4]` = margin) are in fact CORRECT on ptwh0v3k-w5100s, confirmed by counting a real captured RX1 row. The guards added above remain correct and are worth keeping for variable-width rows, but a wrong column index was not the mechanism behind the original blanking.
