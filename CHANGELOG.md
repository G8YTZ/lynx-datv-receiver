# Changelog

All notable changes to Lynx are documented here, in reverse chronological order.

This file starts from 2026-07-29. Earlier changes are recorded in each document's own version history section instead (e.g. the Installation Guide, Web UI Reference) - this centralized approach begins here rather than attempting to retroactively reconstruct everything that came before it.

## 2026-08-04

### Fixed
- **Volume slider now goes to eleven**, per Justin's own Spinal Tap request - runs 0-11 in the Web UI, with 11 kept exactly equivalent to the old 100% (confirmed directly: still exactly unity gain, 0.0 dB). The backend's own `/api/volume` is completely unchanged and still speaks 0-100 percent throughout - the conversion happens purely in the frontend, at the point the slider talks to the API and back, so an existing saved volume (e.g. a prior 100%) correctly loads back in as position 11 on the new slider rather than needing any backend/config migration. The "Default on boot" field was deliberately left as a plain 0-100 number, matching what was actually asked for rather than expanding scope. Tested directly against the real, deployed conversion logic: 11↔100% and 0↔0% at both ends, a round-trip of an existing saved 100% value correctly landing back on slider position 11, and the dB readout confirmed unchanged at both ends.
- **Increased the QRZ name-lookup timeout from 4s to 10s**, per Justin's report of occasional misses on a poorer connection (cellular). Safe to be more generous now specifically because this lookup runs entirely in its own background thread (from the earlier async redesign) - a slower timeout can no longer block the arbitrator or anything else, regardless of how long it takes. Worth knowing: the one remaining cost of a slower connection is the name simply arriving too late to matter - if the lookup takes longer than the notification's own display window (`notification_duration_secs`, 20s by default) the name still won't make it into the notification, since the notification itself has already expired by the time the background thread finishes.
- **WiFi power-save now disabled automatically at startup**, per Justin's request, after tracing a real overnight crash directly to it: the network went completely dead (no SSH, no Web UI) while the rest of the system - including Lynx's own process, confirmed via SIGUSR1 stack dumps showing every thread genuinely idle rather than stuck - stayed fully healthy throughout. `dmesg` explicitly showed `brcmf_cfg80211_set_power_mgmt: power save enabled` at boot, and `brcmfmac` (this hardware's Broadcom WiFi driver) has a well-documented history of exactly this failure. `lynx_start.sh` now runs `iw wlan0 set power_save off` right after its own network-up wait (so `wlan0`, if present at all, has already had time to come up before this tries to configure it), and re-applies it every cycle of the existing health-check/watchdog loop too, in case a later reconnect or roaming event ever resets it - matching the same "cheap enough to just re-trigger" reasoning already used there for re-hiding the mouse cursor. Non-fatal if `wlan0` doesn't exist (a wired-only install) or `iw` isn't installed. Added `iw` to `install.sh`'s dependency list explicitly rather than assuming it's already present - the same class of assumption that caused a real, silent failure with `wtype` on an older install previously, worth not repeating. Justin's own diagnosis directly identified both the specific fix (power-save off) and the likely trigger (a second WiFi network's credentials recently added, increasing background scanning/roaming activity, which fits `brcmfmac`'s known fragility around power-save state transitions) - noted as a plausible contributing factor, not a confirmed one, since it wasn't directly visible in the captured evidence. Wired Ethernet was also recommended as the more robust fix for an unattended, 24/7 receiver, sidestepping this whole class of problem rather than working around it - up to Justin whether to also make that change.
- **Volume control redesigned to dB as the primary unit**, per Justin's follow-up refinement of the earlier 0-11 change - both the main slider and the "Default on boot" field now show dB directly (0.5dB steps, as requested), with the 0-11 Spinal Tap reference kept as a cosmetic "(x/11)" bracket alongside it rather than being the actual functional scale. -60dB is the slider's floor - mpv's own cubic volume scale means percent only asymptotically approaches 0 as dB decreases, so a continuous slider needs a genuine, finite minimum rather than literal -∞; -60dB (10%) is already very quiet and a practical, sensible choice. 0dB remains exactly the old 100% maximum. The backend's own `/api/volume`/`/api/volume/default` are completely unchanged and still speak 0-100 percent - the conversion happens purely in the frontend at the point each value crosses that boundary. The Default on boot field's own "(x/11)" readout updates live as the value is typed/adjusted, matching the main slider's own behaviour, separate from actually saving it. Tested thoroughly against the real, deployed conversion logic: 0dB/-60dB map exactly to 100%/10%, an existing saved 100% correctly round-trips back to exactly 0dB, the 0-11 readout is correct at both extremes and mid-range, the live Default-on-boot readout updates correctly as the field changes, saving it sends the correctly-converted percent to the backend, and loading existing saved percentages correctly populates both fields with valid, in-range dB values.
- **Fixed two leftover "100%" references in the volume section's own explanatory text**, missed in the previous dB redesign - both the "0 dB = unity gain" note and the PPM calibration warning still said "(100%)" instead of "(11)", breaking the joke's own consistency right where it's explained. Fixed to say 11 throughout, matching the actual UI now.
- **New: a Beta update channel**, per Justin's request, mirroring the model BATC Portsdown already uses - regular users stay on the normal, known-working stable branch by default, while anyone who wants to experiment with newer, less-proven code can opt into tracking a separate `beta` branch instead, switchable back to stable at any time. New `GET /api/update/status` field `channel` ('stable'/'beta'), and a new `POST /api/update/channel` endpoint that does the actual switch - genuinely a `git checkout` to a different branch entirely, not just a `git pull` within the current one (an important distinction: pulling always merges into whichever branch is *currently* checked out locally, not necessarily the one named in the command, so switching channels needs an explicit checkout first). Fails safely throughout - if the fetch or checkout fails for any reason, nothing is touched and a clear error is returned; only reboots if the switch itself genuinely succeeded, reusing the same passwordless-sudo-checked reboot pattern as the existing Reboot/Update buttons. Added a defensive self-heal to the existing `POST /api/update/apply` too: it now checks the local branch actually matches the configured channel before pulling, and corrects it first if not - guards against the local checkout ever silently drifting out of sync with the configured channel (shouldn't normally happen, since channel switches always go through the new endpoint's own explicit checkout, but the stakes of a mismatched pull - silently merging beta content into what's meant to be a stable checkout, or vice versa - are high enough to be worth the extra safety regardless). New "Update Channel" card on the Config page: Stable/Beta radio selection, a clear health warning that appears specifically when Beta is selected ("newer, less-tested code... not recommended for an unattended repeater without someone available to fix issues"), and a "Switch Channel" button that confirms before acting and correctly detects "already on this channel" without needlessly triggering a switch+reboot. The main page's version badge now shows a `[BETA]` marker whenever the beta channel is active, visible regardless of whether an update check has run or what it found - so it's never ambiguous which channel is live just from a glance at the main screen. Tested extensively: the core branch-resolution logic for all three cases (no channel configured, explicit stable, explicit beta); the full channel-switch endpoint end-to-end including config persistence and reboot; every failure path (invalid channel rejected, fetch failure fails safely with nothing touched); the defensive self-heal in `update/apply` when the local branch is deliberately mismatched; and the complete frontend flow via the real, deployed HTML/JS - the `[BETA]` marker across all four possible badge states, the live warning toggle, the already-on-this-channel short-circuit, and the full confirm-then-switch flow sending the correct channel to the backend.

## 2026-08-03

### Fixed
- **Fixed a genuine, severe bug in the Shutdown button's confirm dialog text that broke the entire main page's JavaScript**, reported directly by Justin: Presets, Network Streams, and Current Config all stuck on "Loading...". Root cause: the confirm dialog's text contained "you'll", written as `you\'ll` to escape the apostrophe for the JS string it sits inside - but this entire block of HTML/JS is itself a Python triple-quoted string, and Python's own parser resolves `\'` down to a plain `'` before the string is ever sent to the browser at all. By the time the JS parser ever saw it, the backslash was already gone, leaving a bare apostrophe that terminated the JS string early and broke the whole script block - which is why nothing after it (including every `loadPresets()`/`loadLiveStreams()`/`loadConfig()` call at the bottom of the script) ever ran, exactly matching everything staying on its default "Loading..." text. The exact same class of mistake as an earlier bug this session (a JS-style unicode escape breaking Python's own parser), just in the opposite direction - Python and JS have genuinely different escaping rules, and text that's valid in one language's string literal can silently corrupt when it's embedded inside the other's. Manually reading the source code (`grep`/`view`) couldn't catch this at all, since the file on disk genuinely does contain the "correct-looking" `\'` - only actually executing the Python and inspecting the real, resolved output it produces reveals the problem, which is exactly how this was found and confirmed, both before and after the fix. Fixed by removing the apostrophe entirely ("you will need to" instead of "you'll need to") rather than trying to get the cross-language escaping exactly right, which is what caused the mistake in the first place. Swept the entire codebase for any other instance of this same pattern (found none) and validated the actual, real, resolved JavaScript output of all three pages (`/`, `/config`, `/diagnostics`) with a real parser this time, not just a visual read of the source.
- **Hardened `wait_for_mpv_rendering()` against a wedged GPU decoder giving a false "rendering confirmed"**, per Justin's report of a stream switch (via the Knobler) that "swapped OK" but exposed the desktop, recovered only by a full Pi reboot - consistent with an earlier freeze this session traced to a hardware HEVC decoder kernel error (`rpi-hevc-dec ... Missing inuse DPB ent`). This function previously trusted `mpv`'s own "AV:"/"VO:" log markers alone as proof of a genuine render - but those only confirm `mpv`'s own software pipeline is progressing (demuxing, decoding, submitting frames onward), not that a frame actually reached the screen. If an earlier freeze left the GPU decoder itself wedged, a fresh `mpv` process for the next stream could print entirely normal progress markers while the hardware never produces a real frame at all - exactly matching what was reported. Now also checks `dmesg` for that specific decoder error before trusting the markers, scoped only to entries from this specific rendering attempt's own start time (via `dmesg -T --since`) so an old, already-resolved occurrence from hours earlier can never keep incorrectly flagging every future attempt. If detected, treated as an immediate, definite failure (not a timing issue worth retrying within the same call) and logged to the Diagnostics timeline as `mpv_render_hevc_decoder_error`, so a real recurrence now leaves direct, first-class evidence rather than requiring `dmesg` to survive a manual check before the next reboot wipes it. Best-effort throughout: any failure reading `dmesg` itself (permissions, unavailable, etc.) is treated as "no error found" rather than blocking a genuine, healthy render. Tested directly: the normal case (no decoder error) is completely unaffected; a detected decoder error correctly returns a failed render and logs the diagnostic event; a failed/unavailable `dmesg` check gracefully degrades to trusting the markers rather than blocking; the existing timeout-with-no-markers path is untouched; and the `--since` timestamp was confirmed to be correctly scoped to this specific call's own start time.

## 2026-08-01

### Added
- A diagnostic capability for tracking down an intermittent, hard-to-reproduce hang: a confirmed real incident where the Web UI became completely unresponsive while `mpv` (a genuinely separate process) kept running normally - strongly suggesting something stuck inside `lynx_app.py` itself (a held lock, a hung background thread) rather than anything display/GPU-related, but with no direct evidence yet of exactly what. `lynx_app.py` now registers Python's own `faulthandler` on `SIGUSR1`, dumping every thread's current stack trace to `/var/log/lynx/stacktrace.log` on demand - tested directly against a genuinely hung thread before deploying, confirmed to correctly show its exact blocked location. `lynx_start.sh`'s own health-check loop now triggers this automatically right at the moment it detects the web app not responding, capturing the evidence before the process gets killed and replaced, rather than losing it. Known limitation of the automatic trigger: it only fires if `/api/status` itself stops responding - a hang isolated to a different endpoint (e.g. one waiting on `tune_lock` specifically) might not trip it, though the same capability remains available manually (`kill -USR1 $(pgrep -f lynx_app.py)`) regardless.
- The stack-trace log above originally wrote to `/tmp`, which is typically RAM-backed on Raspberry Pi OS - confirmed directly as a real problem when a second freeze incident lost the dump entirely to exactly this, right when it would have mattered most (the system journal has the same volatile-storage issue, noted separately in the install guide's troubleshooting section). `install.sh` now creates a persistent `/var/log/lynx/` directory with the right ownership; both `lynx_app.py` and `lynx_start.sh` prefer it when writable, falling back safely to `/tmp` (tested directly, both branches) rather than failing to start at all on an install that hasn't been re-run through `install.sh` since this was added.
- Dual-watch, Stage 1 (RF + a network stream input covering the same repeater simultaneously, so one receiver can do the job of two): new `lynx_rtmp_probe.py`, a minimal, dependency-free RTMP client for detecting whether a stream input is actively publishing, without decoding any audio/video - watches only the RTMP protocol's own "Stream Begin"/"Stream EOF" User Control messages, the same detection principle Ryde Player uses (confirmed by reading its actual source), but implemented independently after confirming the library Ryde depends on for this (`python-librtmp`) is effectively abandoned - no ARM64/modern-Python wheels, requires compiling against an unmaintained C library. Built and unit-tested against a protocol-compliant mock RTMP server (handshake, chunk framing including all four header-compression formats, AMF0 encode/decode, ping/pong, reconnect-on-drop, and a debounce layer reused from the existing Picotuner-offline pattern) - two genuine bugs were caught and fixed this way during testing, both around the debounce logic failing to commit a state change under specific timing conditions. `lynx_app.py` now starts this as a background monitor (opt-in via a new `dual_watch:` config section) and no longer retunes the Picotuner away from a real signal while a stream plays when dual-watch is enabled, so RF lock and stream-active state are both genuinely, continuously known at the same time - visible together in a new `dual_watch` section of `/api/status`, and a small status line on the main page. Stage 1 is infrastructure only - no priority/arbitration logic between the two sources yet (Stages 2-4, not built). **Not yet validated against the real BATC RTMP server** - only against a mock server built for this purpose; real-hardware testing is the required next step before this is trusted for anything live.
- **Dual-watch confirmed working against the real BATC RTMP server**, on real hardware, same day it was built - a live test transmission correctly flipped `stream_active` from false to true, with `rf_locked` genuinely true at the same moment - something that was never previously possible, since the Picotuner used to always be retuned away the instant a stream started playing.
- **Renamed and generalized to "tri-watch"**, after a genuinely good real-world use case surfaced: two RF sources on the SAME frequency but different symbol rates (a tuner given one specific, known rate to lock onto, rather than scanning a range, does noticeably better on weak signals). The config and `/api/status` shape changed from a fixed "one RF, one stream" pairing to a generic list of up to 3 sources (`tri_watch.sources`), any mix of RF-A, RF-B, and one stream, each independently `enabled: true/false` - so 2 or 3 sources work in any combination, not just the original RF+stream pairing. This is a breaking config change from the original `dual_watch:` key - anyone who set that up needs to move to the new `tri_watch:` shape (see the updated `lynx_config.example.yaml` for the full structure). Verified directly with a realistic 3-source scenario (RF-A locked, RF-B not locked, stream active, all simultaneously correct) before deploying, not just the simpler 2-source case. Still Stage 1 scope - RF sources are tracked but not automatically tuned to their configured frequency/symbol-rate (that's active control, not detection, and stays a Stage 2 item); getting an RF source's configured tuning actually applied still means using Manual Tune by hand for now. Running more than one stream source simultaneously is untested (only ever had one in any real-hardware test so far).
- **A genuine bug in the above, caught before ever reaching real hardware**: the initial tri-watch RF sources were distinguished by `plug` (a/b), but confirmed directly against `_tune_impl()`'s own, existing logic that this was wrong - outside diversity mode, a manual tune always sends `rcv=1` regardless of which plug was selected, so "plug B" in ordinary use still runs through the *same* rcv=1 circuit, not a second one. `picotuner_state_b` (the second receiver's own status) is only genuinely populated during diversity mode, where rcv=1 and rcv=2 are each tuned separately. This would have made any RF source configured with `plug: b` outside diversity mode permanently, silently show "no lock" regardless of actual signal quality. Fixed by keying sources on `rcv` (1 or 2 - the actual receiver circuit) instead, with `fplug` kept as a separate, independent field for Stage 2's future tuning logic. Also corrected an earlier, incorrect claim in this same feature's docs that Manual Tune could already achieve the same-frequency/different-symbol-rate use case by hand - it can't, since it has no way to tune rcv=2 independently outside diversity mode (which forces both receivers to the same symbol rate for combining); that use case genuinely needs Stage 2's own tuning logic to be testable at all.
- One specific piece of Stage 2 pulled forward at Justin's request, since the same-frequency/different-symbol-rate use case genuinely needs it to be testable at all: `tri_watch`, when enabled, now actively tunes every configured, enabled RF source to its own frequency/symbol-rate at startup - and, deliberately, this REPLACES Lynx's existing resume-last-state behaviour entirely for any `tri_watch`-enabled receiver (even with only one source enabled within it), rather than running alongside it. A dedicated repeater receiver should always come up on its configured, correct inputs, not whatever a human happened to be doing before the last restart - a genuinely different, and better, default for that specific use case. This does NOT touch the behaviour for anyone with `tri_watch` disabled - confirmed directly, the new code path returns immediately, leaving the existing, proven resume-last-state logic completely untouched and unreached in that case. New tune commands are sent directly (not via `tune()`/`_tune_impl()`, neither of which can independently tune two receivers to two different values at all - confirmed this directly rather than assume it), reusing rcv=2's own separate command port and the same 0.3s inter-command settling delay diversity-mode tuning already proved necessary. Tested directly with mock UDP listeners standing in for the Picotuner's two command ports, confirming the exact commands sent to each - including two genuinely different symbol rates landing correctly on their respective receivers. Still deliberately does not touch mpv or the display - deciding what's actually worth showing stays Stage 2's job.
- The rest of Stage 2: simple arbitration between `tri_watch` sources. Whichever source goes active first holds the screen; if another goes active while it's still playing, it does NOT preempt - instead, an on-screen notification appears saying something else wants attention, and it takes over automatically once the currently-displayed source finishes. Built as a genuinely isolated, standalone `TriWatchArbitrator` class before it was ever wired to real mpv/Picotuner control, and unit-tested against 7 scenarios directly: idle-to-active, notification appearing while another source is displayed, no duplicate notifications while a source keeps waiting, handover when the displayed source goes inactive, notification expiry after its configured duration, everything-inactive going idle, and a source being able to notify again after dropping out and coming back. Actually switching the display reuses existing, proven machinery - `restart_mpv()` pointed at each RF receiver's own transport-stream port for RF sources, the existing `start_stream()` for stream sources - rather than anything new. Caught and correctly handled a genuine, non-obvious locking hazard here: `start_stream()` acquires `tune_lock` internally while `restart_mpv()` does not (confirmed directly against every other real call site in the file), so the two branches needed different locking to avoid a deadlock.

  The on-screen notification itself: an iMessage-style speech bubble, positioned middle-right on the video output per Justin's direction, with a tail pointing left toward the video content, sized and word-wrapped automatically to fit whatever message text it's given. Colour is Apple's actual system blue (#007AFF) - Justin's own identification, confirmed via search against multiple independent sources rather than just trusted - the same blue iMessage uses for its own outgoing bubbles, replacing an earlier, initial guess at "a similar blue". Message wording is fully configurable - a new, genuinely separate template system from the existing Slack notification's own (that one's built specifically around RF-lock events with fields like MER/margin that a stream source has no equivalent for; wiring the two together properly stays a Stage 4 item). Default RF wording: `"{callsign} is waiting to access {configured_callsign} on {frequency}"`, with `{callsign}` pulled live from the Picotuner's own decode and `{configured_callsign}` from a new, per-source `callsign` config field (since a receiver could `tri_watch` two entirely different repeaters' inputs). Stream sources use plain, user-typed text instead, since there's no live "who's transmitting" data available the way there is for RF. Tested by actually rendering the exact, deployed drawing code (extracted directly from the real file, not a rewritten copy) to real image files at both a short and a genuinely long message length, confirming the word-wrap and bubble sizing hold up correctly in both directions - not yet confirmed how it actually looks composited live over real video on real hardware, which is the one thing still needing eyes on an actual screen.

### Fixed

Now re-triggered periodically from the existing health-check loop, so it recovers automatically instead.

Added to the dependency list - but since `git pull`/`Update Now` only ever pull code and never install system packages, any install that predates this fix won't get `wtype` itself just by updating (`sudo apt install -y wtype` needs running by hand once). `lynx_start.sh` now checks for this explicitly at startup and prints a clear, visible warning with the exact fix if it's missing, rather than failing silently the way it did here.

### Known limitation
- A real, confirmed, intermittent freeze/hang on a Pi 500 - screen frozen (mouse cursor still moves), Web UI unresponsive, `mpv` and the rest of the OS otherwise healthy (no memory pressure, no thermal/undervoltage throttling per `vcgencmd get_throttled`, no gaps in a continuous background watchdog log). Not yet root-caused. Ruled out so far: memory exhaustion, thermal/power throttling, screen blanking (already disabled). The diagnostic capability added above (see "Added") is specifically aimed at catching this properly the next time it happens, rather than continuing to infer from indirect, after-the-fact evidence.

- **New feature: QRZ.com name lookup for tri_watch's waiting-station notification**, per Justin's own request - looks up the waiting station's first name and includes it alongside the callsign. Genuinely needs its own, new credentials rather than the existing QRZ Logbook API key: the callsign-lookup service is QRZ's separate XML Data API, which authenticates with a normal QRZ username/password login (requiring an XML-subscriber-level account) rather than an API key - added as new, clearly-separated config fields, with an explanation in the Config page itself of why these are different from the Logbook key already there. New `qrz_callsign_lookup()` (`lynx_notifications.py`) manages its own session key (obtained via login, reused across lookups, proactively refreshed before QRZ's own ~1hr expiry, and automatically re-obtained if QRZ rejects it as stale mid-lookup), caches results per callsign for 24h (a station's registered name essentially never changes within a session), and is built directly against QRZ's own published XML schema - tested thoroughly with synthetic responses matching that exact format (successful login+lookup, cache reuse avoiding repeat network calls, session-expiry mid-lookup correctly triggering an automatic re-login and retry, bad credentials, callsign not found, and a simulated network timeout - all degrading gracefully to no name rather than ever raising), since there's no way to test against the live service without real credentials. The lookup itself is called synchronously from `_build_tri_watch_message()`, which is safe here specifically because that function only ever runs once per new, already-settled notification (never a hot loop), with a short, bounded timeout (4s) so a slow/unreachable QRZ can never stall things for long. Two new template placeholders - `{name}` (just the name) and `{name_suffix}` (pre-formatted as " (Firstname)", or empty if no name was found/lookup is off) - and the default notification template now uses the latter, so it reads naturally either way ("G8YTZ (Justin) is waiting..." vs. plain "G8YTZ is waiting..." with lookups off or no match) without any awkward empty punctuation. A new, separate toggle (independent of whether QRZ *logging* itself is on) controls whether notifications use this at all. Tested end-to-end: lookup disabled produces the original, clean message with no network activity at all; a successful lookup correctly includes the name; a failed/not-found lookup degrades gracefully with no leftover empty parentheses or other artifacts.
- **Corrected the notification format** - Justin's own first version put the name in parentheses after the callsign ("G8YTZ (Justin) is waiting..."); asked directly whether that matched what he'd actually described, and it didn't - he wanted the name prepended instead ("Justin G8YTZ is waiting..."). Fixed: `{name_suffix}` (parenthetical, trailing) replaced with `{name_prefix}` (plain, leading - carries its own trailing space so it disappears cleanly with no leading-space artifact when no name was found), and the default template updated to match. Re-tested all three cases directly: lookup disabled produces the original, clean message with no network activity at all; a successful lookup now correctly reads "Justin G8YTZ is waiting..."; a failed/not-found lookup degrades gracefully with no leftover space or punctuation artifacts.
- **Fixed a genuine, serious risk in the QRZ notification lookup**: it was being called synchronously inside the arbitrator's own `step()` loop - the same loop that must stay responsive for tri_watch to work at all. A slow or unreachable QRZ could plausibly block it for the better part of a minute (multiple chained network timeouts across login/lookup/retry-after-expiry), stalling every other tri_watch decision - source switching, lock/loss handling, everything - for that entire window. Reported directly as "locked (green) but no picture for ages" plus the desktop-flash symptom returning, both consistent with the arbitrator getting stuck. Fixed by moving the lookup entirely off the critical path: the notification now fires immediately with just the callsign (as it always did before this feature existed), and the QRZ lookup runs in a background thread, updating the message in place afterwards only if the same notification (matched by source_idx) is still the one showing - discarded harmlessly if a different/newer notification has since replaced it. Tested directly with a simulated slow lookup: the message returns near-instantly regardless of lookup speed, the background update correctly applies while the notification is still current, and correctly discards itself when it's gone stale.
- **New: a dedicated QRZ name-lookup test tool**, per Justin's own report that the lookup wasn't working and the log showed nothing at all (`grep qrz_lookup /tmp/lynx_app.log` came back empty - strong evidence the lookup was never even being attempted, most likely because `lynx_app.py` hadn't been restarted since editing `config.yaml`, so it was still running with the old config in memory). New `POST /api/qrz/lookup_test` endpoint plus a matching "Test QRZ Name Lookup" card on the `/diagnostics` page (alongside the existing Logbook test), reporting exactly which pre-condition isn't met (missing credentials, `lookup_for_notifications` off) or the real lookup result, without needing to wait for an actual RF lock or a notification to fire. Deliberately synchronous/blocking, unlike the notification path itself - this is a one-off, user-initiated test request, not something running inside any time-critical loop, so there's no risk here of the concern that motivated making the real notification path asynchronous. Caught and fixed a genuine bug of my own while building this: the new JS function was missing its closing brace, which Python's own syntax check can't catch since it only validates the surrounding string literal, not the JavaScript embedded inside it - found by extracting and validating the actual JS with a real parser (`node --check`), which is now confirmed clean, along with the other two `<script>` blocks in this file checked the same way as a precaution.
- **Fixed a genuine race condition in the QRZ notification-name update** - Justin reported the test lookup tool worked 100%, but the real notification still only showed the plain callsign with no name. Traced it directly: the background lookup thread is started from inside `_build_tri_watch_message()`, *before* that function has even returned its message string back to the arbitrator's own `step()` - which only sets `self.notification` on the very next line after that return. Normally a gap of microseconds, but a near-instant, cached lookup (exactly what happens when the same callsign was just checked moments earlier via the new test tool) could genuinely complete and check `self.notification` before that single assignment had happened at all - finding `None`, and silently discarding a perfectly good result. Fixed by having the background thread wait briefly (up to 2s, checking every 50ms) for the arbitrator to actually set the notification before checking it, rather than checking exactly once, immediately. Tested by directly reproducing the exact race - an instant/cached lookup completing before `self.notification` is set, matching the real, reported failure - and confirming the fix resolves it, plus re-confirmed the message still returns instantly regardless of lookup speed, a genuinely slow lookup still updates correctly afterwards, and a stale/mismatched notification is still correctly left alone.
- **Fixed the "whoever comes up first gets the slot" bug**: the main Web UI status panel (Callsign, Programme, Frequency, MER, etc. for Rx1) was gated on the overall `lynxMode`, switching entirely to show stream info whenever a stream was on screen - correct for normal, single-mode operation where RF and stream are genuinely mutually exclusive, but wrong under `tri_watch`, where Rx1 stays continuously, independently tuned in the background regardless of what's actually being displayed. Whichever of Rx1/stream happened to load first "won" that shared slot, hiding the other's status entirely - exactly matching the reported symptom. Interestingly, the Tuner B panel right below it already had the correct fix for this exact class of problem (shown independently of `lynxMode`, based only on whether `tri_watch` is using Rx2) - Rx1 had just never received the same treatment. Documented directly on the Control card rather than silently left as a surprise.
